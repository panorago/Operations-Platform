# VENDA specification and deployment audit

Audit date: 3 November 2026 (Africa/Harare). Baseline: the user's uploaded **Pasted text.txt**, preserved as `SPECIFICATION.md`.

## Outcome

The eight-route application and its main operational workflows are implemented. The previous GitHub Pages deployment was unsuitable: it served the source entrypoint rather than a Vite-built application, used root-relative asset paths on a repository subpath, and had no API server. This could produce the blank page reported by the user. The build configuration and published files have been corrected.

There are now two explicit targets. The **GitHub Pages preview** is built static output, with browser-local sample data and a visible preview banner. The **full server application** uses Express, authenticated roles, and SQLite, and has a persistent Render deployment blueprint. The Pages preview is not a full production deployment and does not satisfy the brief's shared, authenticated production environment by itself. No live hosting credentials or integration secrets were available in this session. Render account connection/service creation remains an external prerequisite.

## Corrections made in this audit

1. Added a real Pages build, generated deployment assets, `.nojekyll`, correct `/Operations-Platform/` asset URLs, and hash routes. The preview no longer requests a nonexistent `/api` server and does not collect login passwords.
2. Preserved the server-backed build separately so Render still serves the complete application and database. Shared pure domain rules prevent the preview and server order arithmetic from diverging.
3. Linked the eight seed truck manifests to their dispatched seed orders, with product quantities and CSV order references; removed the supplier-catalogue-as-manifest shortcut. Existing user databases are not overwritten to refresh seed records.
4. Added dated reminder schedule previews to credit checkout and scheduled/overdue trigger dates to invoice details. Due-date generation now uses the Harare calendar date.
5. Added blue dispatched-order pills and corrected headline size, navigation section labels, and non-navigation selection border widths.
6. Connected low-stock alerts to prefilled reorders, overdue invoice alerts to payment recording, and sync alerts to dismissal. External reminder statuses now read actual stored provider outcomes rather than always saying unconfigured.
7. Added an exact-subpath, no-backend browser test and CI validation for both builds. Kept generated Pages output checked in so branch-based GitHub Pages can serve it directly.

## Validation and publication evidence

- `npm run build`: full server client build and TypeScript checks.
- `npm run build:pages`: static Pages build and generated root deployment files.
- `npm test`: **19 passed, 0 failed**; domain/provider tests for credit, integer-cent VAT, permissions, payment/cancellation, stock receipt, dates, reminders, and provider behaviour.
- `npm run test:e2e`: **1 passed**, actual Chromium workflow through all eight pages against a fresh SQLite server, including setup-key rejection and first-account creation.
- `npm run test:pages`: **1 passed**, actual Chromium workflow under `/Operations-Platform/` with no API backend; includes route navigation, persisted local settings/orders, credit checkout/reminder preview, linked manifests and AI fallback. The test also rejects browser runtime errors and unexpected `/api` requests.

Exact run outcomes and the pushed commit are reported in the chat after these checks finish. The public Pages hostname and GitHub deployment APIs are denied by this environment's network policy, so a local passing browser run and a successful Git push must not be represented as independently verified remote deployment completion. Refresh the site after GitHub's Pages rebuild; if its publishing source differs, select `main` / `(root)` in repository Pages settings. Render deployment is not completed merely by committing `render.yaml`.

## Remaining production prerequisites

Connect and create the Render service, set the first administrator using its generated setup key, and configure any required live provider accounts. The blueprint uses a paid Starter service and persistent disk; Render presents the cost before confirmation. AI/email/SMS require their respective secure server credentials and sender/recipient settings. No real payment gateway is integrated because the specified payment modal records operational settlement rather than providing a gateway contract. Router v6's moderate upstream advisories remain documented in README; there are no known high-severity production dependency advisories in the last npm audit.
